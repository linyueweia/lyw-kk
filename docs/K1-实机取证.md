# KICKPI K1 (V1.2) 实机取证记录

> 原则：**一切以实机 DTS / 运行中系统为准**。社区仓库 `j3ffs/Kickpi-K1` 仅供参考，
> 实测证明它是从 Radxa Rock 3A 改出来的，错漏较多。

## 0. 板卡标识

| 项 | 值 |
|---|---|
| 丝印 | KICKPI **K1，V1.2** |
| 厂商固件 DT model | `Rockchip RK3568 KICKPI K1A Board`（"K1A"=厂商内部版本代号） |
| 厂商固件 compatible | `rockchip,rk3568-kickpi-k1a` → 适配用 `kickpi,k1` |
| SoC | RK3568B2 |

## 1. 存储与分区（GPT，Rockchip Android 式）

```
mmcblk0 58.2G:
  p1   4M  uboot     前16字节 d00d feed...（Rockchip 引导器格式）
  p2   4M  misc      全零
  p3  64M  boot      d00d feed...
  p4 128M  recovery  d00d feed...
  p5  32M  backup    全零
  p6  58G  rootfs    ext4 ← 当前根
  boot0/boot1 各 4M，全零
nvme0n1 119.2G → p1 hermes-work(ext4) /work；PCIe 总线 0002（pcie3x2 @fe280000）
cmdline: storagemedia=emmc  root=PARTUUID=614e0000-0000
```

## 2. 启动链（从 eMMC uboot 分区读出的厂商 U-Boot 环境）

```
U-Boot 2017.09 (Dec 09 2025)  board=evb_rk3568  bl31-v1.44
kickpi,cmd-uboot                            ← KICKPI 改过 U-Boot
LBA64 = "RKNS"                              ← BootROM 读取的 idblock
boot_targets=mmc1 mmc0 mtd2 mtd1 mtd0 usb0 pxe dhcp
rkimg_bootdev=if mmc dev 1 && rkimgtest mmc 1; then ... Boot from SDcard; elif mmc dev 0; ...
"Found IDB in SDcard" / "Rockchip SD Boot Image"
```
→ BootROM → eMMC LBA64 idbloader → eMMC uboot 分区的厂商 U-Boot → **先探 SD(mmc1)**
→ **SD 卡启动可行** ✓（与 T68M 当年 TF 启动同机制）

## 3. 网络

| 项 | 实机实测 |
|---|---|
| eth0 | = `ethernet@fe010000`，MAC 9e:e7:fa:63:d2:ce，**已协商 1000Mb/s Full** ✓，驱动 rk_gmac-dwmac/st_gmac，错包 0 |
| eth1 | = `ethernet@fe2a0000`，MAC 9a:e7:fa:63:d2:ce，当前无连接 |
| PHY（两个都是） | **Maxio MAE0621A-Q2C，phy_id `0x7b744411`**；各挂自己的 mdio、地址都是 0 |
| RGMII 延迟 | eth0(fe010000)：**tx=0x2f rx=0x39**；eth1(fe2a0000)：**tx=0x21 rx=0x3c** |
| reset-gpio | eth1: `<&gpio3 0x1b ...>`；eth0: `<&gpio3 0x07 ...>`；reset-delays-us=<0 0x4e20 0x186a0> |
| mdio 结构 | **每个 ethernet 节点内部各有一个 `mdio` 子节点 + `phy@0`** |
| phy-mode / clock | `rgmii` / `clock_in_out="output"` |

**驱动要求**：Maxio 是**内核树外驱动**，必须打补丁 + `CONFIG_MAXIO_PHY=m`（模块，不是内建：
内建在"在线更新换内核"时无法补救；模块化才有 DKMS + postinst 钩子 + 开机自愈，
否则两个网口全哑且 DWMAC 报 `DMA engine initialization failed`）。

## 6. 与社区 DTS 的差异（判定）

| 项 | 社区 | 实机 | 结论 |
|---|---|---|---|
| 网口 tx/rx 延迟 | 0x3c / 0x4f | 0x2f/0x39、0x21/0x3c | ❌ 错 |
| mdio | 独立 &mdio0/1 | 每个 ethernet 内嵌 | ❌ 结构不同 |
| 风扇 | gpio-fan + fan_en_h | **无** | ❌ 凭空编的 |
| SATA | 无 | 3 节点 + ata1 | ❌ 缺失 |
| USB3 | 无 | usbdrd/dwc3 | ❌ 缺失 |
| WiFi | 仅 sdio | SWT6621S 树外驱动 | ❌ 驱动缺失 |
| RTC hym8563 | 有 | 有 | ✅ 对 |
| 摄像头/MIPI | 有 | 有(gc5035) | ✅ 方向对 |
| pi6c / vcc_cam 命名 | 有 | 无 pi6c | ❌ 别家板子的 |
| LED | 仅 1 个 work-led | work-led + 一串 | ⚠️ 不全 |

## 7. 适配必须补的三项（实机有、社区无）

1. **SATA**：DTS 节点 + armbian 侧 `BOOTCONFIG_SATA` / 内核 `AHCI` 配置
2. **USB3 父 glue 节点**：`&usbdrd` / `&usbhost`（T68M 当年就栽在没开父节点）
3. **SWT6621S WiFi/BT 树外驱动**（性质同 Maxio PHY）

## 9. 2026-10-14 第二轮实机定案（全部在 KICKPI K1 卡上系统 + 串口逐秒取证）

### 9.1 NVMe 冷启动失败：pcie30 PHY 上电时序

| 时刻 | 证据 |
|---|---|
| t≈13.94s | `rockchip_p3phy_rk3568_init: lock failed 0x6890000, check input refclk and power supply` |
| t≈15.07s | `pcie30_avdd0v9: 900 mV, enabled` / `pcie30_avdd1v8: 1800 mV, enabled`（**晚 1.1 秒**） |
| — | `phy init failed -110` → `dw-pcie: invalid resource` → `rk-pcie -ETIMEDOUT` → `rk_pcie_remove+0x98/0x1d0` Oops → `probe failed -22` |

- 驱动侧依据：`phy-rockchip-snps-pcie3.c` 的 `regmap_read_poll_timeout(..., SRAM_INIT_DONE, 0, 500)`
  —— PHY 内部 SRAM 初始化只等 **500µs**，供电没到位就必然超时。
- **有效修法**：① DTS 给槽电源 `vcc3v3_pcie` 挂 `gpio0 RK_PD4(pin28)` + 补两路 `pcie30_avdd*` 常开 regulator；
  ② 开机自愈单元重绑定 `rk-pcie`。
- **反例（不要做）**：给 `&pcie30phy` 加 `phy-supply = <&pcie30_avdd0v9>` → PHY 永久 `deferred probe`，比原问题更难救（v9 实测）。
- 结果：重绑定后 `15.752 Gb/s available PCIe bandwidth, limited by 8.0 GT/s PCIe x2`、`nvme0n1 238.5G`。

### 9.2 网口角色真源 = roceos.db（不是 factory-env.json）

`/opt/roceos/data/roceos.db` 三张表实机取值（用户定义 WAN=eth0 / LAN=eth1 后）：
`network_interfaces` → `wan1|WAN1|wan|eth0|dhcp`、`lan1|LAN1|lan|eth1|static|192.168.100.1|255.255.255.0`；
`interface_bindings` → `wan1/["eth0"]`、`lan1/["eth1"]`；`lan_configs` → `nic_ids=["eth1"]`。
改库 + 重启后 eth0 从上游拿到 DHCP、eth1 = 192.168.100.1。**注意各台机器 MAC 不同，不能写死。**

### 9.3 EEE/LPI：只挂 NetworkManager dispatcher 不够（第 4、5 层）

本板 roceos 用 **ifupdown-ng**（`networking.service`），不经过 NM；只挂 dispatcher 时，
重配网络后 EEE 被重新协商打开 → 端口恢复**每 15~20 秒 Up/Down** 抖动（journal 逐条可查：
`38.6s Up → 216.9s Down → 222s Up → 237.2s Down → 241.3s Up…`）。
补 `if-up.d` 钩子 + 30 秒周期兜底 timer 后：`Link Up 1 / Down 0`、两口 `EEE status: disabled`。

### 9.4 WiFi（SWT6621S）：结论 = 差异在内核，暂止

DT（厂商原厂 `wireless-wlan` 胶水、电源脚 gpio3 RK_PD5、`sdio_pwrseq` 去 reset-gpios 等）、
树外驱动、固件、加载规则全部与飞牛线等价后，**6.1 vendor 内核 SDIO 仍不上卡**（400kHz 枚举不应答），
而飞牛 6.18 同硬件可跑 → 移植 = 换 6.18 同源内核（影响 maxio/EEE/NVMe 整套）。用户决定不再追。

### 9.5 运维教训（踩过的坑，写进技能）

- **换内核前必须看 boot 分区余量**：本板 boot 分区是 **256MB FAT16**（卷标 `armbi_boot`），
  常只剩几十 MB；往里再拷一份内核（40~50MB）会 **ENOSPC 静默截断**（本次备份被截成 18MB，不可引导）。
- **内核可从官方镜像精确恢复**：`iNextOSA_26.2.1_Kickpi-k1_..._6.1.115.img` 的 boot 分区是
  **FAT16 @ 偏移 0x1000000**（OEM 名 `mkfs.fat`、类型串在 0x36 不在 0x52，按 FAT32 找会漏；
  用卷标 `armbi_boot` 定位最快 —— FAT16 卷标在 BPB 偏移 **0x2B**）。
  `IMAGE` 首簇 5、47747584 字节、md5 `23a984ccb742e1e32df85156867d22df`。
- **eMMC（mmcblk0）全程只读**：脚本里加设备白名单断言，挂载后 `findmnt` 二次确认。
